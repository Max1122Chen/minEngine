> **状态：Planned，仅登记，未开始设计。** 本文件只回答「引擎还缺哪些常规表达力能力、大致怎么归类」，

## 为什么登记而不是直接补

本轮任务书 §6 只点了三项（9-slice / FillAmount / 文字垂直对齐），但它们不是孤立缺失，
而是「UI/Sprite 表达力」这一类能力整体薄弱的表现。只补这三项会让引擎呈现「打补丁」的形状：
字段零散、语义不成体系，下次再来一个需求又要重新定义一遍。
因此先登记完整的能力面，等排期空出来再整体设计。

## 设计时必须先定的问题（交给正式设计阶段）

1. **字段放哪**：`ImageComponent` 逐项加字段，还是抽出 `UIImageStyle` 之类可复用的样式结构？
2. **材质参数槽位**：现有 `UVRectU0..V1` 是固定槽位；新增参数要同步扩槽位表与缓存 key，否则「改了不生效」。
3. **序列化兼容**：全部走 `ME_PROPERTY` 追加、缺省取默认；**禁止重排既有枚举值**。
4. **9-slice 走图内 UV 还是 9-quad 网格**：前者零网格改动但有半像素误差，后者精确但要新顶点布局。
5. **UI 与 Sprite 的边界**：9-slice、裁剪、排序这些两边都要，语义必须统一（否则又是两套实现）。
6. **与材质材质实例开销的关系**：每 widget 一份材质实例，参数增多会放大分配成本（编译风暴已修，但边际成本仍在）。
